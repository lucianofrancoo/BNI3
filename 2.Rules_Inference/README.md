# 2. Boolean Rules Inference (`2.Rules_Inference/`)

This module is responsible for inferring the logical relationships (Boolean rules) between different genes/nodes over time based on the binarized data from the previous stage. The algorithm leverages **Gene Expression Programming (GEP)**, capable of discovering robust and complex underlying regulatory interactions matching the expression dynamics.

The pipeline in this step consists of four consecutive scripts: inference, analysis, evaluation, and visualization.

**Scripts 1 → 2 → 3 are chained automatically.** Running the inference script alone carries the run all the way through to the evaluated ruleset: it triggers the analysis, which in turn triggers the rule combination evaluator. Each link can be cut with a flag (`--no_analysis`, `--no_evaluation`), and every script still runs standalone. Only the visualizer (4) is always launched by hand.

## Pipeline Scripts and Usage

### 1. Rule Inference (`1.BNI3_Boolean_Rules_Inference.py`)
This is the core algorithm. It runs the GEP evolution process to infer the Boolean transition rules using the original raw data and the binarized dataset. It supports optional Neural Network (MLP) validation and regulator connectivity penalization (favoring biological parsimony around $K \approx 2$).

**Basic Usage:**
```bash
python3 1.BNI3_Boolean_Rules_Inference.py -i ../1.Binarization/Example/Counts_lite.tsv -i_binary ../1.Binarization/Example/Counts_lite_binarized_SSD.tsv -o Example/
```
*Note: This script runs multiple independent repetitions per gene and then automatically triggers the analysis module, which in turn triggers the evaluator — so this single command produces `rules_by_gene_evaluated.tsv` without further intervention.*

Relevant flags:

| Flag | Effect |
|---|---|
| `--no_analysis` | Stop after inference (skips analysis *and* evaluation) |
| `--no_evaluation` | Run the analysis but stop before the evaluation |
| `--eval_confidence` | Forwarded to the evaluator as `--confidence`; use `0` for a single sampling batch |
| `--eval_processes` | Forwarded to the evaluator as `-n` |

The binarized matrix given in `-i_binary` is forwarded automatically to the evaluator, so the data-concordance criterion is always available in a chained run.

**Run log and the next command.** Once the chain finishes, the run writes `rules_inference_log.txt` in the output directory: the inputs, the target genes, the settings, how many experiments succeeded, and the attractor command for what it just produced.

```
Next step - attractor analysis
------------------------------------------------------------
python3 /path/to/3.Attractors/BNI3_Attractorator.py \
    -i /path/to/output/rules_by_gene_evaluated.tsv \
    -b /path/to/Counts_lite_binarized_SSD.tsv \
    -O /path/to/output --predecessors 2
```

The same command is printed to the console. Both inputs are already known at that point: the binarized matrix is the `-i_binary` this stage was given, and the rules table is whichever of the two this stage wrote — the log is written *after* the chain, so it names `rules_by_gene_evaluated.tsv` when the evaluation ran and `rules_by_gene.tsv` when `--no_evaluation` stopped it early.

### 2. Results Analysis (`2.BNI3_Analyze_results.py`)
This script parses the multiple output iterations generated by the inference step. It looks at the resulting `.tsv` metrics and extracts the best Boolean rules based on maximum correct transitions (`n_correct`), regulator penalizations, and MLP validation scores.

**Basic Usage:**
```bash
python3 2.BNI3_Analyze_results.py -i Example/
```
*(This is typically called automatically by the Inference script, creating a `rules_by_gene.tsv` file in your output directory)*

After writing that file, this script automatically chains the evaluator (step 3) on it. When running it standalone, pass `-m` so the evaluator can score data concordance — without it that criterion is 0 for every combination and the ranking falls through to the attractor metrics:

```bash
python3 2.BNI3_Analyze_results.py -i Example/ -m ../1.Binarization/Example/Counts_lite_binarized_SSD.tsv
```

Use `--no_evaluation` to stop after the rules table.

### 3. Rule Combination Evaluator (`3.BNI3_Evaluate_rules.py`)
Because multiple candidate rules can tie for the top fitness score per gene, this script evaluates permutations of the best Boolean rules. It tests these combinations analytically (calculating basin entropies, cycle lengths, distances from Kauffman's optimal $K=2$, and final state concordance) to rank and determine the absolute best, functionally unified ruleset for your network.

**Basic Usage:**
```bash
python3 3.BNI3_Evaluate_rules.py -i Example/rules_by_gene.tsv -m ../1.Binarization/Example/Counts_lite_binarized_SSD.tsv
```
*This will output two files:*
*   `evaluation_results.tsv`: The full ranking and attractor metrics for all evaluated combinations.
*   `rules_by_gene_evaluated.tsv`: The definitive winning ruleset, ready to be passed to the Attractor stage.

#### Performance update (2026-06-04)

The attractor-search engine was rewritten to eliminate the main bottleneck. Previously, for each rule combination the code iterated over all $2^N$ network states one by one, calling Python `eval()` with string replacement **$N \times 2^N$ times** per combination (~106,000 calls for a 13-gene network). This made large evaluations take several hours.

**What changed:**

| Component | Before | After |
|---|---|---|
| State transition | Per-state Python `eval()` loop | Vectorized numpy: `eval()` called once per rule over all $2^N$ states as boolean arrays |
| Attractor finding | Re-evaluates rules at every simulation step | O(1) array-lookup traversal of a precomputed transition table |
| Basin size counting | Undercounted: states absorbed into earlier trajectories were silently skipped | Correct: all $2^N$ states assigned to their attractor via `np.unique` |
| Process pool | `imap_unordered` with default chunksize | `chunksize` tuned to reduce IPC round-trips |

**Measured speedup (13 genes, 20,000 combinations, 8 processes):**

| | Time per combination | Total wall time |
|---|---|---|
| Before | ~4,479 ms | ~186 min |
| After | ~34 ms | ~1.4 min |
| **Speedup** | **~133×** | |

The public API (`evaluate_rule_combinations`, output file format, all CLI flags) is unchanged. The old `find_attractors_for_ruleset` function is kept in the file for reference.

#### Auto-parallelization update (2026-06-05)

Previously the default number of worker processes was hardcoded to `8`. The script now auto-detects the number of available CPU cores (`mp.cpu_count()`) and uses all of them by default, maximizing throughput without any manual tuning.

| | Before | After |
|---|---|---|
| Default `-n` / `--processes` | `8` (hardcoded) | `None` → `mp.cpu_count()` at runtime |
| Example on a 32-core machine | 8 workers | 32 workers (~4× more parallelism) |

#### Rule evaluation cache + Numba JIT (2026-06-05)

Two additional optimizations layered on top of the vectorized engine:

**Rule evaluation cache** — all unique `(gene, rule)` pairs are evaluated once before the main loop and stored as precomputed numpy bool arrays. Workers receive the cache via pool initializer, so `eval()` is never called inside the hot loop regardless of how many combinations are evaluated. For a 13-gene network with 20,000 combinations this replaces up to 260,000 `eval()` calls with 22 dict lookups.

**Numba JIT (`_assign_attractors_jit`)** — the O(2^N) state-traversal loop is decorated with `@njit` so Numba compiles it to native machine code on first call. Uses fixed-size numpy array buffers instead of Python dicts, making the attractor assignment ~10–30× faster. Requires `pip install numba`; the script falls back to pure Python automatically if Numba is not installed.

| Component | Before (v1.1.0) | After |
|---|---|---|
| Rule eval inside hot loop | `eval()` × N per combination | dict lookup (cache, zero eval) |
| Attractor traversal | Pure Python loop + dicts | Numba-compiled native loop |
| Pool worker init | Default | Sets cache + warms up JIT once per worker |

New dependency: `numba` (optional — graceful fallback if absent).

The `-n` / `--processes` flag still works to override manually if needed:
```bash
python3 3.BNI3_Evaluate_rules.py -i Example/rules_by_gene.tsv -m ../1.Binarization/Example/Counts_lite_binarized_SSD.tsv -n 16
```

#### Combination limits, `--top-results`, and execution timing (2026-06-05)

Several usability improvements:

- **Increased combination limits**: The absolute cap was raised to 50,000,000 and the default sampling target to 5,000,000. On a 64-core machine the script evaluated 5 million combinations in ~4 minutes at ~19,700 combos/sec.
- **Simplified strategy selection**: The previous 3-strategy system included a `reduce_both` fallback that could silently cap rules per gene to 3. This was removed. There are now only 2 strategies: evaluate ALL if it fits within the time budget, or random-sample if it doesn't. `top_n` (rules per gene) is **never reduced** — all max-score rules are always kept.
- **`--top-results`** (new flag, default `10000`): Limits how many rows are written to `evaluation_results.tsv`. Without this, evaluating 5M combinations produced an unmanageable 1.6 GB file. Use `--top-results 0` to write everything.
- **Execution time summary**: Printed at the end of each run — wall time in MM:SS format, total combinations evaluated, throughput (combos/sec), and ms per combination.

```

  Combinations   : 5,000,000 evaluated
  Throughput     : 19,700 combinations/sec
  Per combination: 0.05 ms

```

#### Statistical confidence and adaptive batching (2026-06-05)

When evaluating a random sample of 5M combinations from a space of 484M, there is some probability that the single best combination was never sampled. The script now estimates this probability and runs additional batches automatically until a target confidence is reached.

**The coverage formula:**

If K out of M total combinations achieve the minimum score and you sample n, the probability of finding at least one is:

```
P = 1 − (1 − K/M)^n
```

K is unknown, but can be estimated from the sample: if k combinations in your n-sample share the best score, then K/M ≈ k/n. Substituting:

```
P ≈ 1 − (1 − k/n)^n ≈ 1 − e^{−k}
```

The n and M cancel — **confidence depends almost entirely on k** (how many times the best score was observed):

| k | Confidence |
|---|---|
| 1 | 63% |
| 2 | 86% |
| 3 | 95% |
| 5 | 99.3% |
| 7 | 99.9% |
| 10 | 99.995% |

**Note on which score is used:** k is counted from `composite_score` (the pre-normalization attractor quality metric), not `final_score`. `final_score` is normalized within each sample so its values shift when the sample changes — using it for cross-batch comparison would be unstable. `composite_score` is a raw weighted sum of attractor metrics (n\_basins, cycle\_length, concordance, fixed\_point\_ratio) that is computed before normalization and is stable across batches.

**Adaptive batching:**

By default, the script evaluates an initial batch (up to 5M combinations), checks k, then adds more batches if k < 7 (i.e., confidence < 99.9%). Each additional batch targets exactly the number of samples needed to reach k = 7. The total is capped at 3× the initial batch size (e.g., 15M) to prevent runaway in cases where the optimum is extremely rare. Batches are **additive** — new batches only evaluate fresh combinations and accumulate on top of previous results; no work is ever repeated.

Example output (two-batch run):

```
   Batch 1 complete — 5,000,000 total | k=2 | confidence=86.5%
   Batch 2: 7,500,000 more combinations (k=2, confidence so far: 86.5%)...
   Batch 2 complete — 12,500,000 total | k=6 | confidence=99.7%
────────────────────────────────────────
  Combinations   : 12,500,000 in 2 batches
  ── Statistical coverage ──────────
  k (top score)  : 6 occurrences of best score
  Confidence     : 99.75%
  For 99%      : 11,513,000 total (done)
  For 99.5%    : 14,030,000 total (1,530,000 more needed)
  For 99.99%   : 23,026,000 total (10,526,000 more needed)
────────────────────────────────────────
```

If k is large after the first batch (e.g., k=10 → 99.995%), no additional batches run. For exhaustive evaluation (all combinations fit within the budget), coverage is reported as 100%.

Use `--confidence 0` to disable adaptive mode (single batch only), or change the target:
```bash
# Require 99.9999% confidence (k ≥ 14)
python3 3.BNI3_Evaluate_rules.py -i Example/rules_by_gene.tsv -m ../1.Binarization/Example/Counts_lite_binarized_SSD.tsv --confidence 0.99999
```

#### Output column update (2026-06-05)

The `rules_by_gene_evaluated.tsv` file gained a new column **`n_top_combos`**, replacing the previous `EvalScore` column.

| Column | Description |
|---|---|
| `Score` | GEP fitness score — how well the rule reproduces observed transitions |
| `n_top_combos` | How many of the best-ranked combinations used this rule for this gene |

`EvalScore` (the combined evaluation score) was the same value for every row in the file — all entries come from combinations that tied for the best score — so it carried no per-gene information. `n_top_combos` is genuinely gene-level: a rule with a higher count was used more consistently across the top combinations, making it the more robust choice when multiple rules tie for a gene.

Rows within each gene are now sorted by `n_top_combos` descending, so the most-consensus rule appears first. The full `final_score` per combination is still available in `evaluation_results.tsv`.

#### Lexicographic tie-break cascade (2026-09-21)

The ranking no longer collapses the eight criteria into a single weighted sum. Combinations are now compared **criterion by criterion, in priority order**: the first criterion that differs decides the winner, and the remaining ones are never consulted.

**Why this changed.** In the weighted sum, a small gain on one metric could outweigh a real loss on another, because each metric was min-max normalized within the evaluated sample and the weights (0.20, 0.15, 0.12, 0.08 …) put them on arbitrary comparable scales. On the `Example` dataset this produced a concrete failure: the winner agreed with the observed final timepoint in **11 of 13 genes**, while a combination agreeing in **12 of 13** was ranked second and discarded. The margin was 0.000729 — the NOT-operator penalty (weight 0.08) outweighed data agreement (weight 0.10) because their normalized ranges differed. Two fewer `~` operators were traded for one more gene disagreeing with the data.

**The cascade order** is defined once in `CASCADE_CRITERIA` near the top of the script; edit it there to re-prioritize.

| # | Criterion | Direction | Rationale |
|---|---|---|---|
| 1 | `final_state_concordance` | higher | Agreement with the observed final state — the only criterion anchored in data |
| 2 | `n_basins` | lower | Fewer basins = more interpretable |
| 3 | `avg_cycle_length` | lower | Shorter attractors |
| 4 | `fixed_point_ratio` | higher | Prefer fixed points |
| 5 | `basin_entropy` | lower | One dominant basin |
| 6 | `k_distance_from_2` | lower | Kauffman's K ≈ 2 |
| 7 | `total_literals` | lower | Simpler rules |
| 8 | `total_nots` | lower | Less repression |

Data agreement goes first because it is the only criterion grounded in observation; the other seven encode priors about what a network *should* look like. Parsimony still decides in practice — it simply acts among networks that already fit the data equally well, instead of against them.

**Prerequisite fix — concordance now covers cyclic attractors.** `final_state_concordance` used to be computed only over fixed points, so every cyclic network scored 0 *by construction* rather than by disagreeing with the data. Harmless as one term in a weighted sum; fatal as the first level of a cascade, where it would have eliminated all cyclic networks in round one. Concordance is now the best match across **all** attractors (for a cyclic attractor, its best-matching state is used). A new informative column, `concordance_basin_frac`, records the basin share of the attractor that produced the match — a match in a tiny basin is weaker evidence than the same match in the dominant one. It does not participate in the ranking.

**Statistical confidence now matches the ranking.** `k` used to be counted on `composite_score`, a different metric from the one selecting the winner. The consequence was measurable: the `Example` run reported `k=1063 | confidence=100.0%`, yet the combination with the best `composite_score` was *not* the winner — it ranked second, and among the 52 combinations sharing that "100 % certified" score the `final_score` ranged from 0.0247 to 0.0726. `k` is now counted on the full cascade key, so the coverage estimate describes the ranking actually used.

The honest number is much lower. Same dataset, same 5 M sample:

| | Before | After |
|---|---|---|
| `k` | 1063 | 2 |
| Reported confidence | 100.00 % | 86.47 % |
| Samples needed for 99 % | "done" | ~11.5 M |

Because adaptive batching reacts to the lower `k`, a default run now adds batches until the 3× cap (15 M) instead of stopping at 5 M — roughly 13 min instead of 4 min on 64 cores. Use `--confidence 0` for a single 5 M batch.

**Compatibility.** `final_score` and `composite_score_old` are still written to `evaluation_results.tsv` for comparison with earlier runs, but they no longer rank anything. Note `final_score` is normalized within the evaluated sample, so its values are **not** comparable between runs — only the ordering within one run ever was. The `rules_by_gene_evaluated.tsv` format, the `n_top_combos` column and all CLI flags are unchanged.

**Measured effect on `Example`** (identical 5 M sample, seed 42): the cascade selects the 12/13-gene combination that the weighted sum discarded. **12 of the 13 genes receive a different rule.** This is expected — with 3.1 × 10¹⁵ possible combinations and thousands of near-ties, the identity of the single winner is not stable, and changing the criterion reshuffles it substantially. The per-gene consensus column `n_top_combos` remains the more robust reading of the output than any single winning combination.

Steps 1 → 2 → 3 now run as one command. Previously the inference script triggered the analysis, but the rule combination evaluator had to be launched by hand; `rules_by_gene_evaluated.tsv` was never produced by an unattended run.

#### Gene-name handling, exact pruning, hill climbing (2026-09-24)

**Two silent failures fixed first.** The inference script sanitizes gene names to valid Python identifiers (`re.sub(r'\W|^(?=\d)', '_', col)`) because rules are evaluated with `eval()`; `AT1G01360 (RCAR1)` becomes `AT1G01360__RCAR1_` and `SnRK2.8` becomes `SnRK2_8`. The evaluator did not, so:

1. Rule genes never matched matrix columns, and `final_state_concordance` scored **0.00 for every combination** — silently disabling the top criterion of the ranking cascade. On a real 15-gene run this went unnoticed through 15,000,000 combinations and 68 minutes.
2. The first column was treated as an index whenever its name did not start with `G`, `AT`, `LOC` or `ENSG`, which **swallowed the first gene** of any matrix using plain symbols like `RCAR1`.

Both are fixed. Names are now sanitized identically on both sides, the index column is detected from its *values* (a gene column contains only 0/1) rather than from its name, and two guards abort loudly instead of degrading quietly: zero overlap between rule genes and matrix columns, and non-binary columns in the binarized matrix.

Sanitization is many-to-one, so it can create ambiguity: `GEN.1` and `GEN_1` both become `GEN_1`, as do `SnRK2.8`, `SnRK2 8` and `SnRK2-8`. Colliding names are now an error naming the offenders, not a silent overwrite.

**Exact prune on the first criterion** (`prune_rules_by_final_state`, on by default, `--no-prune-concordance` to disable). `final_state_concordance` reaches its maximum of 1.0 exactly when an attractor state equals the observed final state `s*`. The simplest way is for `s*` to be a fixed point — and that condition **factorizes over genes**: `s*` is a fixed point iff `rule_g(s*) == s*_g` for each gene independently. So the winning subset is found with `sum(n_g)` rule evaluations instead of enumerating `prod(n_g)` combinations, and since concordance ranks first, everything outside it is dominated and can never win. This is an exact prune, not a heuristic.

*Worked example, suitable for adapting into a methods section.* Take the gene `HB7` and one of its candidate rules, `AIT1 & ~ABF3`. Read the values of `AIT1` and `ABF3` from the observed final state `s*`, evaluate the rule, and compare the result with the value `HB7` itself has in `s*`. If they differ, that rule cannot belong to any network in which `s*` is a fixed point, and it is discarded — regardless of which rules the other fourteen genes use. Each gene is tested independently, one rule at a time, against one state.

This is why the cost is a **sum** over genes rather than a product. On the Drought network the fifteen genes contribute 166, 154, 133, 128, 85, 79, 75, 61, 61, 59, 42, 42, 42, 33 and 29 candidate rules: summing them gives 1,189 single-state evaluations, while multiplying them gives the 3.41 × 10²⁷ combinations that would otherwise have to be searched. The 1,189 evaluations leave 724 surviving rules and a space of 8.14 × 10²², roughly 42,000 times smaller.

Only the concordance criterion factorizes this way. The attractor criteria — basin count, cycle length, basin entropy — couple all genes at once, since they depend on the trajectory of the whole network, so no comparable shortcut exists for them.

On the 15-gene Arabidopsis Control network:

| | |
|---|---|
| Search space | 4.53 × 10²⁷ |
| After pruning | 8.88 × 10²³ (**0.02 %**) |
| Cost | **1,145 rule evaluations** |

The prune is skipped automatically when any gene keeps no rule: `s*` is then not a fixed point of any combination, concordance is below 1.0 everywhere, and the discarded rules would still be in contention. (This is what happens on the bundled `Example`.)

**Random-restart hill climbing, now the automatic choice** (`--search auto`, the default). The strategy is picked from the problem size: enumerate the whole space when it fits, otherwise climb. Uniform sampling is never selected automatically — on any space large enough to require sampling, hill climbing won in every comparison below. `--search sample` forces the old behaviour, and is the only mode the `1 − e^{−k}` confidence estimate applies to; `--search hill` forces climbing, though an enumerable space is still enumerated because that strictly beats searching it.

| Space | `--search auto` picks | Reproducibility reported |
|---|---|---|
| Fits in the budget | Exhaustive enumeration | Coverage 100 % |
| Too large | Hill climbing | Restart convergence |
| Too large, `--search sample` | Uniform sampling | Confidence `1 − e^{−k}` |

Uniform sampling scales badly against 10²⁷: 15,000,000 independent draws typically end with k=1, a single isolated best. One hill-climbing sweep instead evaluates every single-gene change of the current combination — about `sum(n_g)` candidates, ~1,100 for 15 genes — moves to the best, and restarts from a fresh random point once no single swap improves the cascade key. Evaluating all genes' alternatives as one batch (steepest ascent) also keeps the worker pool fed.

Measured on the same network, same machine:

| Strategy | Budget | Time | Winner's NOTs | Combos at best key |
|---|---|---|---|---|
| **Hill climbing** | **60,000** | **14 s** | **2** | **1,182** |
| Uniform sampling | 60,000 | 13 s | 6 | — |
| Uniform sampling | 1,000,000 | 207 s | 4 | — |

Hill climbing with 60,000 evaluations beats uniform sampling with 1,000,000 — a better network, 16× fewer evaluations. All three tie on concordance, basins, cycle length and K, so the NOT count is what separates them.

**What the method is called, for citation.** The algorithm implemented here is **random-restart steepest-ascent hill climbing**, also described in the literature as multi-start local search. It belongs to the family of *stochastic local search* methods in combinatorial optimization. Its three components have distinct standard names, worth separating in a methods section:

| Component as implemented | Standard term |
|---|---|
| Move to the best neighbour, not the first improving one | *steepest-ascent* (or *best-improvement*) hill climbing |
| Neighbourhood: change the rule of exactly one gene | *single-variable change* / *1-exchange neighbourhood* |
| Restart from a fresh random point at a local optimum | *random-restart* / *multi-start* |

Canonical references:

- Russell, S. & Norvig, P. *Artificial Intelligence: A Modern Approach* — the local-search chapter, where "random-restart hill climbing" is defined under that name.
- Hoos, H. H. & Stützle, T. (2004). *Stochastic Local Search: Foundations and Applications*. Morgan Kaufmann — the reference treatment.
- Martí, R., Resende, M. G. C. & Ribeiro, C. C. (2013). "Multi-start methods for combinatorial optimization". *European Journal of Operational Research*, 226(1), 1–8 — specific to the restart component.

Two neighbouring methods this is **not**, in case a reviewer asks: it is not GRASP, which builds each start with a randomized greedy construction rather than drawing it uniformly; and it is not Iterated Local Search, which perturbs the incumbent solution instead of restarting from scratch. Verify the reference details before citing.

**Live progress.** While climbing, the script prints a line per restart:

```
   Restart 15 | 92,458/120,000 evals | 0/15 genes fixed | 2,219 tied | missed basin <26.4%
```

`genes fixed` counts genes whose rule is the same across every combination tied at the best key, and `tied` counts those combinations. Both reset when a strictly better optimum appears and grow as ties accumulate, so they move in sawtooth fashion rather than shrinking: the search space itself does not shrink during the climb, the prune already did that once, up front. `missed basin` is the one quantity that decreases monotonically — the bound below.

**Stopping criterion: restarts, not evaluations.** The evaluation budget used to be a hardcoded `TARGET_COMBINATIONS_FOR_SAMPLING = 5_000_000`, unrelated to anything about the problem — the same 5M whether the space was 10¹⁵ or 10²⁷, the landscape smooth or rugged. The function even computed a time-based budget and then discarded it. That number could not be justified in a methods section, so it no longer decides anything in hill mode.

Restarts are the statistically meaningful unit: the coverage guarantee is `(1 − x)^R`, which depends on how many independent starting points were drawn, not on how many combinations each climb happened to touch. So the criterion is now a target on coverage, and the restart count follows from it:

$$R = \frac{\ln(1-\text{conf})}{\ln(1-x)}$$

| Largest basin that could be missed | 95 % conf | 99 % conf | 99.9 % conf |
|---|---|---|---|
| 5 % | 59 | 90 | 135 |
| 2 % | 149 | 228 | 342 |
| **1 %** | 299 | 459 | **688** |
| 0.5 % | 598 | 919 | 1,379 |
| 0.1 % | 2,995 | 4,603 | 6,905 |

`--target-basin` (default `0.01`) sets `x` and `--confidence` (default `0.999`) sets the confidence. **There is no automatic evaluation cap**: the restart target is what ends the run, because a cap filled in by the defaults could only stop the search short of the guarantee it had just promised. Pass `--max-combos` to impose one explicitly, and the run will say which of the two stopped it — naming the shortfall when the cap fired first.

**Runs are reproducible.** Hill-climbing starting points are seeded (`--seed`, default 42). They previously were not: the sampling path was seeded but this one never was, so the same inputs gave different restart counts and convergence rates on every invocation — 528 restarts at 66.3 % convergence one run, 464 at 19.6 % the next, on identical data. Two runs at the same seed now match exactly, and changing the seed is the way to check how stable the answer is:

| | Restarts | Evaluations | Convergence | Winning key |
|---|---|---|---|---|
| seed 42 | 135 | 984,385 | 91.1 % | identical |
| seed 42 (repeat) | 135 | 984,385 | 91.1 % | identical |
| seed 7 | 135 | 981,554 | 90.4 % | identical |

Note that convergence rate is **not comparable across runs that found different optima**. A better optimum usually sits in a smaller basin, so a run that finds a better answer can report a lower convergence rate than one that settled for a worse one. Compare the `best_*` columns of the log before comparing convergence.

This is what makes the run reportable: *"restarts were performed until any optimum not reached was guaranteed, at 99.9 % confidence, to occupy a basin below 1 % of the starting space (688 restarts)."* Measured effect on the Drought network at `--target-basin 0.05`: 135 restarts, 828,517 evaluations, **2 min 16 s instead of 17 minutes**, with 97.8 % of restarts converging on the best key.

**Time estimates are now calibrated.** The old estimate assumed a flat 300 combinations/second/core regardless of network size, and was wrong by 3.9× on a 15-gene network (predicted 4.3 minutes, took 17). Cost per combination is dominated by building the transition table over all 2^N states for N genes, so throughput now scales as `1/(N · 2^N)`, calibrated against a measured run. It predicts an independent 13-gene run to within 2 %.

**Coverage statistic for hill climbing.** The `1 − e^{−k}` formula assumes uniform random sampling and does not apply to a guided search, but hill climbing supports a stronger statement. Restarts *are* independent uniform draws — of a **starting point** — so what they bound is basin size: an optimum reachable from a fraction `x` of starting points survives `R` restarts unseen with probability `(1 − x)^R`. Solving for a target confidence gives

$$x = 1 - (1-\text{conf})^{1/R}$$

which the script now prints:

```
  ── Hill-climbing coverage ────────
  Restarts       : 577
  Reached best   : 26 (4.5% of restarts)
  Combos at best : 27
  Any optimum missed must have a basin smaller than:
    at 95%   conf:   0.52% of starting points
    at 99%   conf:   0.79% of starting points
    at 99.9% conf:   1.19% of starting points
  Missing one as reachable as this best: p = 2.8e-12
```

This is a better guarantee than the sampling one, because it is **not circular**: `1 − e^{−k}` estimates K from the very sample being validated and so only describes the best value already seen, whereas basin size is a property of the landscape. The statement "any optimum I missed is reachable from under 0.79 % of starting points" is checkable and reportable.

A low convergence rate is itself informative. 4.5 % means a rugged landscape where most restarts settle on worse local optima — the best found is real (26 independent restarts confirm it) but it sits among many near-misses. The script flags rates under 10 %.

**Search trace (`evaluation_log.tsv`).** Written next to the results on every run, `--no-log` to disable. The results file says *what* the answer is; this one says *how it was reached*, in one row per restart (hill climbing) or per batch (sampling) rather than millions of rows.

Provenance sits in `#` comment lines — inputs, gene count, strategy, prune statistics, the cascade in force, prioritized regulators, worker count — so the file is self-describing and `pd.read_csv(path, sep='\t', comment='#')` reads the table directly.

| Column | Meaning |
|---|---|
| `restart` / `batch` | Step number |
| `evaluations_total` | Combinations evaluated so far |
| `improved` | 1 if this restart beat the previous global best |
| `genes_fixed` | Genes whose rule is identical across every combination tied at the best key |
| `combos_tied_at_best` | How many combinations are tied there |
| `missed_basin_99` | Bound on the basin of any optimum still unseen |
| `best_<criterion>` | The best key so far, as readable metric values — one column per cascade criterion |

The `best_*` columns are what make the trace worth keeping: they show which criterion improved at each jump, so a run that looks like it converged early can be checked for whether it was still refining parsimony or genuinely stuck.

```
restart  evaluations_total  improved  genes_fixed  combos_tied_at_best  missed_basin_99
      1               6643         1            1                  143         0.990000
      2              11274         0            0                  313         0.900000
     ...
     25             150000         0            0                 3331         0.168236
```

That example is worth reading closely: the best key was found on the very first restart and never beaten in 25 more, yet ties kept accumulating to 3,331 with **no** gene settled. A flat optimum like that is a result to report as underdetermined, not as a network.

**Optional priority regulators** (`--priority-regulators HB6,MYB44,ABF3`). The names go straight in the command, so the whole pipeline can be launched in one line; a file with one name per line is still accepted for long lists. Names are sanitized like everywhere else, so `AT2G22430 (HB6)` and `AT2G22430__HB6_` both work. Adds a criterion counting how many regulators of a combination come from that list — known transcription factors, say. It is inserted as criterion **#6**: after data fit and attractor structure, before parsimony. So it never overrides how well a network reproduces the data or how clean its dynamics are; it only chooses among networks already tied on those, preferring the one built on known regulators before preferring the simplest one.

It is a preference, not a filter: rules without the listed regulators stay in the running. On the test network, prioritizing HB6 and MYB44 raised priority edges from 12 to 18 while concordance, basins, cycle length and fixed-point ratio stayed at their optima — only parsimony gave ground. Move `_PRIORITY_CASCADE_POSITION` to `8` to make it a last-resort tie-break instead.

**Reading `rules_by_gene_evaluated.tsv`.** When several combinations tie on every cascade criterion, the file lists all the rules they use, which is why some genes get one row and others several. That was previously unexplained. Two columns now make it self-describing:

| Column | Meaning |
|---|---|
| `n_top_combos` | How many of the tied best combinations use this rule for this gene |
| `n_tied_combos` | How many combinations tied in total (same for every row) |
| `consensus` | `n_top_combos / n_tied_combos` |

Per gene the counts sum to `n_tied_combos`, so the reading is direct:

- **One row with `consensus` 1.00** — the cascade settled that gene outright; every tied combination uses that rule.
- **Several rows** — those alternatives are indistinguishable under all criteria. The gene is genuinely ambiguous, not arbitrarily assigned, and `consensus` says how dominant the leading rule is.

The console now says the same in words, naming which genes stayed ambiguous and how strong their leading rule is. A gene sitting at 0.35 consensus is a result to report as uncertain, not a rule to publish as settled.

All three options are reachable from the **first** script too, so a single command carries them through inference, analysis and evaluation:

| Script 1 / 2 flag | Reaches the evaluator as |
|---|---|
| `--eval_search {auto,sample,hill}` | `--search` |
| `--eval_restarts N` | `--restarts` |
| `--priority_regulators A,B,C` | `--priority-regulators` |
| `--eval_confidence P` | `--confidence` |
| `--eval_processes N` | `-n` |

```bash
# Whole pipeline in one command, TFs prioritized.
# The search strategy is chosen automatically, so --eval_search is not needed.
python3 1.BNI3_Boolean_Rules_Inference.py \
    -i Counts.tsv -i_binary bin_matrix.tsv -o results/ \
    --priority_regulators HB6,MYB44,ABF3

# Evaluator alone
python3 3.BNI3_Evaluate_rules.py -i rules_by_gene.tsv -m bin_matrix.tsv \
    --max-combos 100000 --priority-regulators HB6,MYB44,ABF3
```

#### `-p` now reaches the evaluator (2026-09-25)

`-p/--processes` sized the GEP inference pool only. The chained evaluator has its own `--eval_processes`, and when that was absent it fell back to `mp.cpu_count()` — so on a machine with more logical cores than the user asked for, an explicit `-p` was silently overridden halfway through the pipeline. Running `-p 32` on a 32-core / 64-thread Threadripper produced `Starting hill-climbing search with 64 CPU processes`, which was accurate: the evaluator really did spawn 64 workers.

An explicit `-p` now carries over to the evaluator. The bare default (4) does not, so a run that never mentions `-p` still lets the evaluator use the whole machine rather than crawling on four workers. `--eval_processes` overrides both.

| Invocation | Evaluator workers |
|---|---|
| `-p 32` | 32 |
| `-p 32 --eval_processes 8` | 8 |
| no `-p` | all logical cores |
| `--eval_processes 16` | 16 |

Note that `mp.cpu_count()` counts *logical* cores. The evaluator's inner loop is CPU-bound bitwise work over 2^N states, which gains little from SMT and can lose to it through cache pressure; on a 32-core / 64-thread machine, `-p 32` is worth benchmarking against the 64-worker default rather than assuming more is faster.
